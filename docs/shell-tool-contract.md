# `run_command` 契约

Harness 的**唯一**一个直接操作系统的工具。v1 的其余工具(读文件、写文件、编辑、按内容搜索、按文件名搜索)都建立在它定义的这套约定之上。

## 设计立场:搬运事实,不做判断

这个工具负责**把通道修好**,但**不解释通道里的内容**。

| 它做 | 它不做 |
| --- | --- |
| 把输出编码钉成 UTF-8 | 判断退出码是否意味着"失败" |
| 超长输出头尾保留并标注省略量 | 跟踪 `cd` 后的工作目录 |
| 超时杀进程并如实回报 | 识别"命令不存在"并建议替代写法 |
| 原样返回 stdout、stderr、退出码 | 重试或改写模型的命令 |

分界线是:**通道保真属于工具,语义判断属于模型。** 编码错了工具就是在传垃圾,必须修;而"端口空闲所以 findstr 退出 1"是模型自己就能判断的事,工具替它判断只会掩盖信息。

## 接口

```
run_command(
  command: string,        // 必填。要执行的 PowerShell 命令。
  cwd?:    string,        // 可选。工作目录,默认会话启动目录。
  timeout?: number        // 可选。毫秒。默认 120_000,上限 600_000。
)
```

返回给模型的内容(三段始终都在,即使内容为空):

```
exit code: 0
--- stdout ---
hello from powershell
--- stderr ---
```

标签是必需的,不是装饰 —— 没有标签,模型无法区分"stdout 为空"和"stderr 为空"。

**行尾归一化属于通道处理:** 输出里的 CRLF 统一成 LF,每段末尾的空白裁掉。PowerShell 输出 CRLF,而模型的其余输入是 LF;不归一化会让 `\r` 混进模型看到的内容里。这不违反"不解释语义"—— 和编码修复同类。

## 进程模型:每次调用一个全新进程

**不存在跨调用的状态。** 每次调用启动一个新的 `powershell.exe`,执行完即退出。

推论,必须写进工具描述让模型知道:

- **`cd` 不会保持。** 要换目录,用 `cwd` 参数,或者在同一条命令内串联:
  `Set-Location src; Get-ChildItem`
- **`$env:X = "1"` 不会保持。** 要设环境变量,在同一条命令内设定并使用。
- **不存在"上一个命令的 shell"。** 每次都是干净的。

为什么不做持久会话:见 `docs/adr/0005-shell-tool-reports-facts-does-not-interpret.md`。要点是状态污染不可控 —— 一个任务里的 `cd` 会静默改变下一个任务的行为,而这类 bug 只在长会话里显形。

## 通道处理

### 输出编码

每次调用在模型命令之前注入:

```
[Console]::OutputEncoding = [Text.Encoding]::UTF8; $OutputEncoding = [Text.Encoding]::UTF8;
```

默认控制台代码页是 **936(GBK)**。不注入的话中文输出与报错会变成乱码,而**乱码的报错模型无法自我纠正** —— 它拿到的是 `�Ҳ���`,不是"找不到"。

**解码必须双路:** 若某条命令触发了 PowerShell **解析级**错误(如 `&&`),整串无法解析,前导不生效,输出仍是 GBK。因此解码端先试 UTF-8,出现替换字符则回退 GBK。实测 352 条命令里只漏了 1 条,但那 1 条证明了兜底是必要的。

### 输出截断

保留头部 **8000** 字符与尾部 **4000** 字符,中间插入明确标记:

```
… [省略 138204 字符] …
```

头尾都留的理由是实测的:命令的上下文在头部(列目录的结果),而**失败原因常常在尾部**(`npm install` 的报错就在最后几十行)。只留一头总会丢掉最该看的那部分。

截断必须是**显式标记**,不能静默 —— 模型需要知道自己看到的是不完整的。

### 超时

- 默认 **120 秒**。
- 模型可通过 `timeout` 参数请求更长,**上限 600 秒**。超出上限按上限处理。
- 超时后杀掉进程,并给出**独立的一段**标注,而不是留空输出 —— 空输出会被模型误读成"命令成功但没有结果",而事实是命令根本没跑完:

```
exit code: (超时终止)
--- stdout ---
<可能不完整的输出>
--- stderr ---
<可能不完整的输出>
--- 超时 ---
命令在 120000 毫秒后仍未返回,进程已被终止。上面的输出可能不完整。
```

- 交互式命令(如不带 `-m` 的 `git commit`)会挂到超时。这是可接受的:上限就是为此设的。

## 不做的事

以下每一条都是刻意的不做。**不要在没有重开 ADR-0005 的情况下"修好"它们。**

- **不解释退出码。** `netstat | findstr :8080` 在端口空闲时退出 1,命令完全正确。工具原样透传,由模型判断。实测中 10 条失败命令里 8 条是这个成因 —— 若工具擅自判定为失败,这 8 条会被记成错误,而它们其实都对。
- **不跟踪 cwd。** 从任意命令里推断工作目录(命令可能含子 shell、管道、变量拼接)是一层会持续产生 bug 的推断。
- **不重试、不改写命令。** 模型看到原始结果后自己决定下一步。
- **不做智能错误分类。** 不区分"命令不存在"与"命令失败"并给建议 —— 那是模型读 stderr 就能做的事。
- **不内置危险命令拦截。** 那属于权限层,在工具**之上**,不在工具之内。见规格的权限一节。

## 测试面

这是 v1 唯一打真实系统的工具,也是**副缝**(见规格的 Testing Decisions)。不 mock。

覆盖:

- 命令构造与参数传递(`cwd`、`timeout` 是否正确生效)
- stdout / stderr 分离捕获,空输出时标签仍在
- 退出码原样透传(含"命令正确但返回非零"的情形)
- 编码:中文输出、中文报错、解析级错误下的 GBK 回退
- 截断:头尾保留、省略量标记的准确性、边界值(恰好等于上限)
- 超时:确实杀进程、返回超时标记而非空输出
- Windows 路径:盘符、反斜杠、空格、中文目录名

断言的是**外部可观测行为**(返回了什么),不是内部实现(调用了哪个函数)。
