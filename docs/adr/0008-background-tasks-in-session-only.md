# 0008 后台任务表只在会话内、不落盘、不往对话里注入消息

状态:接受(v2-11)

## 背景

角色多起来之后,"派出去一件事、自己在一边接着干"成了自然需求:子 agent 翻二十个
文件要半分钟,主对话干等它,用户能做的只有等。于是有了后台派发 —— 立刻返回一个
任务 id,活儿挂在一边继续跑,回头再来收账。

要落这个能力,得先回答三个问题:任务状态放在哪、跑完的结论怎么回到对话里、后台
任务要不要权限确认通道。

## 决定

**一、任务表只在进程内存里,绝不落盘。**

子 agent 手上的消息数组、它读过的文件、它攒下的结论,全都只在这一场会话里有意义。
写到磁盘上,下一次启动读回来的是一个**没有历史的孤儿**:它记得自己查过什么,却不
知道当时为什么查、后来结论怎么被用了。跨会话续跑不是"后台任务"这个功能想要的东西,
它是另一件事(会话持久化),该有自己的一张票。

代价说实话:进程一退,没取走的结论就没了。这是有意的 —— 免得用户以为它还在。

**二、后台任务的结论不注入主对话,由 `task_status` 主动来取。**

看上去"跑完自动把结论插进对话"更贴心,但它会破坏压缩器的一条根本假设:
**每个 assistant 消息里的 toolCalls,都能在紧接着的 tool 消息里找到成对的 id。**
后台任务完成的时间点不在任何一次工具调用的返回路径上 —— 往对话里插一条消息,就会
让某次调用与它的结果之间多出别的东西;压缩器按"成对"来裁剪历史时,裁掉一半就再也
对不上了。这个不变量是整条压缩链的地基,不能为了顺手牺牲掉。

所以后台任务的结论停在任务表里,要它就得问 —— 这条路上消息序列与普通派发完全一样。

**三、后台任务没有确认通道:需要用户点头的操作一律拒绝。**

按批准是要占用终端那一行输入的。后台任务跑到一半弹一个确认,用户正在打字 ——
两边抢同一行。所以它在**装配时**就按"问不到人"来(工具集照旧过守门,只是批准函数
一律返回 false),而不是运行时才发现问不到。拒绝时的文案也要如实:不能说成
"用户没有批准这次操作",因为压根没有人被问过。需要用户点头的活,请在前台派。

**四、`background` 不进 `tasks` 批量形态。**

批量本来就是并发跑的,再套一层"后台的后台"只会让人分不清哪个 id 对应哪一项。
要逐个跟踪,分开调用。

**五、续跑(`task_followup`)按同一个角色重新装配,起点是它自己那趟的消息数组。**

"冷启动"与"续跑"是同一个函数的两种入参(history 为空 / 非空),不是两套实现 ——
续跑唯一多做对的事就是没把历史丢掉。装配重新走一遍,所以角色文件改过就用新版:
文件是唯一事实来源,追随旧装配会让"我明明改了提示"变成一个查不出来的怪现象。
只有已经跑完的任务能追问(还在跑的插话会把它自己的对话搅乱,失败的那趟没有可续的
历史)。

## 后果

- 任务表相关的一切都不许碰磁盘。有一个测试直接读源码断言
  `core/task-registry.ts` 里没有 `from 'node:fs'` —— 一旦有人给它加持久化,这条会红。
- 后台任务的成本行不走 `subagent-done` 事件(事件一响,屏幕上就会出现一条不属于
  任何一次工具调用的输出),改为记在任务表里,`task_status` 连结论一起报。
- 后台派发不继承当轮的 `AbortSignal`:用户按中断,该停的是等着它的这次对话,
  不是它 —— 不然"后台"就名不副实。
- 任务表是**会话级**对象:一个会话一张,`createTaskTools` 保证派、查、追问三件套
  共用同一张 —— 分开建表的话,`task` 派出去的任务 `task_status` 就查不到。
