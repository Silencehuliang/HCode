# Provider 是原生适配器,不经由 OpenAI 兼容网关

我们直接对话各厂商自己的 API,在其前置一个 `Provider` 接口,一个厂商一个适配器。我们**不**把所有东西归一化成 OpenAI 线格式再指向一个转换网关。对这个项目而言那条捷径格外显眼:作者此前就亲手造过这类网关(`gemini-balance`、`workbuddy2api-panel`),复用那套模式本可以省掉近一半的适配工作量。

它同时也会抹掉那些让每个模型值得被支持的厂商特性 —— Anthropic 的 prompt caching 与 extended thinking,以及各家自己的流式事件形状。一个表达不了这些的 Harness 会被压到最小公约数上,而那个天花板恰恰是一个以**国内模型友好**做差异化的产品坐不起的位置。

## 考虑过的方案

**归一化成 OpenAI 线格式,放到网关后面。** 否决:造起来最便宜,但所有厂商特性要么不可用、要么变成漏风的特例 —— 而且转换的 bug 仍然由我们承担。

**统一到某一家的 Anthropic 兼容端点上**(GLM 提供这类端点正是为此)。否决作为**主**路径:那等于让一个厂商的 API 形状成为我们的内部模型,是同一个最小公约数问题换了个名字。作为单个 Provider 的实现细节,它仍然有用。

## 后果

- 新增一个厂商意味着写一个适配器及其测试。要为它留预算,**它不是一处配置改动**。
- `Provider` 接口从一开始就必须宽到能承载 caching 与 thinking 控制。事后再加宽要动每一个适配器 —— 这正是当初值得提前定义接口的那个不对称性。
