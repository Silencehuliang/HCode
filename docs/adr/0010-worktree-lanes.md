# 0010 worktree 车道:会写文件的角色去独立检出里干活

状态:接受(v2-13)

## 背景

v2 的角色里,只读的那些(explorer / reviewer / planner)天生安全:它们翻文件、给结论,
碰不到东西。但真正要改代码的角色一进 v2 就带着一个没解决的问题 —— 它和用户共用同一个
工作区。用户回到编辑器前才发现它顺手重排了三个文件,那时候"哪一处是它改的"已经说不清,
而且它可能正跑在一趟会被推翻的思路上,用户的编辑却已经和它的改动缠在一起了。

隔离方案有两条路:进程级隔离(容器、远程机器)和文件系统级隔离(overlay、worktree)。
这一版要的是后者里最不起眼的那一个。

## 决定

**一、车道 = 一间 git worktree,由角色文件里一行 `worktree: true` 开启。**

前置条件(`rev-parse --show-toplevel`)不成立、或者 `worktree add` 失败,就把 git 的原话
加两条出路回给模型,并且**一趟都不跑**。在不 git 的目录里用车道角色,是配置和现实不合,
该当场说清,而不是让子 agent 在用户的工作区里"凑合跑一趟"。

**考虑过的另一种做法:ProjFS overlay(把改动层叠在只读基座上)。** 没采用,理由是它要
驱动一个 Windows 组件、要管理员权限、要处理"哪几层可见 / 层间删除怎么表示"的一堆边角,
而收益只是省下"复制一份检出"的磁盘。git worktree 是用户本来就有的东西(磁盘上共享
object store,实际只多出一份工作树),而且出事时用户看得懂:`git worktree list`、
`git diff`、`git merge`,全是它已经会的命令。

**二、车道目录开在仓库旁边,不在仓库里面。**

路径是 `dirname(repoRoot)/.hcode-worktrees/<仓库名>-<分支名>`。放进仓库里面(比如
`.hcode/worktrees/`)会让三件事同时坏掉:

- 主对话的 `find_files` / `search_content` 会连副本一起翻 —— 搜索结果里每个文件出现两遍,
  而且改在副本里的那一份看起来"没生效"。
- `git status` 里永远挂着一坨未跟踪目录,用户的仓库不再干净。
- 主对话看到 `.hcode/worktrees/<x>/src/a.ts` 会以为那是项目里的路径,顺手去改它。

放在外面,用户的工作区**一个字都没变**,包括 `git status` 是空的。代价:磁盘上多一个仓库
旁边的兄弟目录,以及它得由收尾负责拆掉(见第五、六条)。

**三、相对路径钉在车道上 —— 这是车道能成立的另一半。**

子 agent 手上还是那几个工具,但它说"读 `src/a.js`"时,读的必须是车道里的那一份。做法是
按工具**对模型呈现的 schema** 数据驱动改写:声明了 `path` / `cwd` 的字段才动,给了相对
路径就拼到车道根上,没给且非必填就填成车道根(否则工具会退到 `process.cwd()`,也就是主
工作区),绝对路径不动,没声明这类字段的工具原样过。

少这一步的后果不是"差一点":子 agent 会一边"在车道里",一边把文件写进主工作区 —— 车道
给了虚假的安全感,比没有车道更糟。数据驱动的意义是以后加工具不必回来改车道代码,但**新
工具若换一个字段名叫路径,它就静默地不受车道保护**,这是这条决定的已知代价。

**四、合并策略只做一件事:产分支,人工合。**

收尾把车道里的改动做成一次提交(提交信息 `${角色名}: ${描述}`,回看分支时不用猜是谁干的),
然后**不自动合并**。结论后面挂的那段话是写给主对话模型看的,所以它明说不许自己合:
"合不合由用户决定 —— 把分支名报给他,别自己合进来"。三档操作都给出来:
`git diff HEAD..<分支>`、`git merge <分支>`、`git branch -D <分支>`。

自动合并被拒的理由:车道存在的全部意义是让用户有机会**先看**再决定。自动合回去等于把
隔离变成了"延迟发生的污染",而用户还是没看过那份 diff。

**五、收尾必须在所有出口上发生:跑完、抛错、被打断。**

所以它是 try/finally 的形状而不是"跑完了顺手清理"。`closeLane` 承诺**永不抛**:提交失败、
`git worktree remove` 失败(Win 上编辑器、杀软、索引器都可能正攥着车道里的文件)一律变成
结论后面的一行留痕,带上 git 的原话、分支名、目录路径和用户自己能跑的那条命令。结论本身
照常交回 —— 收尾出问题不该让一整趟白跑。

**六、有未提交改动时绝不删分支;一点改动都没有、目录也拆干净了,才顺手删掉那条分支。**

一条和 HEAD 一模一样的分支留着只是攒垃圾。但只要有任何一步没走顺(暂存失败、提交失败、
目录没拆掉),现场一律保留 —— 那可能是用户唯一能救回改动的地方。

**七、车道不是权限的旁路。**

车道角色照样过守门器、照样受用户的 `permissions` 规则约束,角色层照样只能收紧。想让它
在车道里改文件不逐次弹窗,正确做法是用户在 `settings.json` 里写
`"permissions": { "write_file": "allow" }` —— 那是**用户**放宽天花板,不是 harness 替
车道开后门。车道里开着两个自相矛盾的组合会被当场拒:`worktree` + `permission: read-only`
(只读角色改不了文件,开车道只是让它的搜索范围少掉主工作区的代码)、`worktree` + 后台派
(车道要"跑完立刻收尾",后台任务的收尾时刻不在任何人手上)。

## 后果

- `AgentDef` 多一个 `worktree?: boolean`。它是全文件**唯一**一个"值看不懂就报错、并且不
  注册这个角色"的字段:别的字段写错最坏是"没生效",这一个写错最坏是"用户以为在车道上、
  其实子 agent 正在改他的工作区"。见 [ADR-0007](0007-agents-as-markdown.md)。
- 派发路径拆成 `prepareRun`(装配,含开车道)与 `executeRun`(跑 + 收尾)。`prepareRun`
  因此从同步变异步 —— 唯一原因是开车道要问 git。
- 新增 `src/core/lane.ts`(开车道 / 收尾 / 系统提示 / 路径重定位)与它的测试。测试里有三条
  **真 git** 集成测试(临时仓库里真 `git init` / 真 worktree):断言改动落在分支上、主工作区
  `git status` 为空、车道目录消失、无改动不留分支、以及"把 remove 那一步弄失败"之后的行为
  —— Windows 文件锁没法在测试里稳定复现,能测的是遇到它之后的行为。
- 只读角色那三个内置角色与车道无关(它们本来就不改文件),车道是给会写文件的角色准备的。
- **已知局限,如实记下**:进程被杀(按 Ctrl+C 之后直接退、关终端、`/exit` 时还在一趟车道里)
  时,那间开着车道的收尾不会发生,于是在用户仓库旁边留下一个车道目录和一条分支。没有做
  "下次启动自动清扫":那是拿用户机器上的东西猜意图,而车道里可能正躺着一次未被取走的改动。
  留痕与文档把"自己清"的命令写清了:目录名里就带仓库名与分支名,`git worktree list` 一眼
  看得见,`git worktree remove --force "<路径>"` 就能拆。
