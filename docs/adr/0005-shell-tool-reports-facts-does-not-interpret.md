# shell 工具搬运事实,不解释语义

`run_command` 每次调用启动一个全新的 `powershell.exe`,**不保持任何跨调用状态**;命令的退出码、stdout、stderr **原样透传给模型,工具不做判断**。分界线是:**通道保真属于工具,语义判断属于模型。** 编码错了工具就是在传垃圾,必须修;而"端口空闲所以 `findstr` 退出 1"是模型自己就能判断的事,工具替它判断只会掩盖信息。

完整接口见 `docs/shell-tool-contract.md`。

## 考虑过的方案

**持久 PowerShell 会话。** 否决:`cd` 与 `$env:` 能跨调用保持,更接近人用终端。但**状态污染不可控** —— 一个任务里的 `cd` 会静默改变下一个任务的行为,而这类 bug 只在长会话里显形,正是最难查的那一类。而且它让测试面对一个有状态的进程,与本项目"测机制不测 agent"的取向冲突。实测两个模型都主动在同一条命令里串联(`Get-Location; Get-ChildItem`),从未假设过持久化 —— 这个能力不被需要。

**工具推断退出码语义**(识别 `findstr` / `grep` 的"无匹配 = 1"并标为 `no-match`)。否决:那是一份要持续维护的、按命令逐个积累的知识库,而且会**替模型做它自己就能做的判断**。实测 352 条命令里 10 条失败,其中 8 条正是"命令正确但退出码非零";若工具擅自判定为失败,这 8 条会被记成错误,而它们其实都对 —— 掩盖信息比透传更危险。

**自动跟踪 cwd**(从命令里解析 `cd` 并应用到下次调用)。否决:命令可能含子 shell、管道、变量拼接,推断必然出错,而错误的工作目录会让后续每条命令都静默跑偏。

## 后果

- **`cd` 不保持是刻意的,不是缺陷。** 换目录用 `cwd` 参数,或同一条命令内串联。不要在没有重开本 ADR 的情况下加上持久化。
- **退出码不解释是刻意的。** 不要给工具加"智能失败判断"。模型读得到 stderr,它自己做这个判断比工具做得好。
- **但编码必须由工具修。** 这与"不解释"不矛盾:乱码的报错是**通道损坏**,模型拿到 `�Ҳ���` 无法自我纠正,那不是判断问题,是传输问题。
- 工具接口因此很小(directly 三个参数),测试面也小 —— 这是有意的,它是 v1 唯一打真实系统的工具。
