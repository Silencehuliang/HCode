# 0011 Council:同一个问题并行问多家,一个没有工具的记录员出共识报告

状态:接受(v2-14)

## 背景

到 v2-13 为止,hcode 已经把"角色"做成一等概念:角色文件、白名单、模型绑定、并行派发
(v2-07)、成本可见(v2-06)全都在。但所有角色的 `model` 都指向**一家**模型 —— 用户问一个
拿不准的问题,拿到的是那一家的一次回答,而它是不是错的、有没有别家会说"这不对",用户
无从知道。

国产模型之间可靠性的差异不小(同一个问题,一家给出一条踩坑的路,另一家给出一条能跑的路,
是很常见的事),而用户手上往往同时有几家的密钥 —— 本地网关里 GLM 和 DeepSeek 就都配着。
把"同一个问题同时问几家、再说清它们哪儿一致哪儿不一致"做成一个动作,是这套东西现成的
零件(三角色适配器 + 并行派发 + 结构化输出)拼起来就能得到的东西。

## 决定

**一、council 是一个工具,不是角色。**

角色是"我派你去做一件事",council 是"这件事我要几个独立判断"。它是动作,不是职位,
所以不进角色名册、不进角色白名单的取材范围(`allTools`)。REPL 层的 `@council` 是它的
入口糖,展开排在角色点名**之前** —— 否则模型会先把它当角色名去找。

**二、议员和记录员的工具集都是空的。**

问的是"你怎么看",不是"你替我查"。给议员工具,每一家会走各自的探索路径,最后的分歧里
就混进了"谁翻到了什么文件"这种噪声,而不是对同一个问题的判断差异 —— 那样得到的多元,
是环境差异,不是模型差异。提示词里明写「你没有工具,看不到这台机器上的文件」,是为了让
它别假装查过。

代价:用户必须把材料(代码片段、报错原文、已试过的路)一起贴进来。入口文案里说了这件事。

**三、配不出两家的密钥,就不注册这个工具。**

一家的"共识"只是绕远路的提问。而工具一旦出现在工具表里,模型就会去用 —— 空转一轮、
再向用户解释"我需要两家"是完全可能发生的事。宁可不给。

**四、一家没答上来不拖垮全局,全都答不上来就不合成。**

失败那家在报告里保留位置并标注「(这一家没答上来)」,同时进合成 prompt(记录员该知道
有一方缺席)。全失败时直接回错误清单,不去跑合成 —— 没有可合成的东西,再花一次钱只是
把错误包一层。

**五、合成用主对话那一家,输出约定只有两节:`共识` / `分歧`;不合格只重试一次。**

重的活(各家原话)已经落在报告里了,合成本质是"挑拣"而不是"再答一遍",所以对它的要求
只有两个字段和一次重试。两次都不合格时,把各家原话原样回给用户 —— 报告是给用户看的,
不是回给模型的措辞,所以不复用 `output-contract` 里那句对着模型说话的失败文案。

**六、成本逐家报,合计另起一行,并写明"这是几家的账"。**

不写清楚,用户会拿一次 council 的账单去对照一次普通提问,得出"怎么突然贵了四倍"的结论。

## 后果

- `council` 进了 `NO_BLAST_RADIUS`(permission.ts):议员的工具集是空的,它花的是 token,
  不是用户的文件。与 `task`/`skill` 同类,不该弹审批框。
- 每家的 token 数是**估算**(`estimateMessageTokens`),不是账单。报告里如实标"估算"。
- 议员 `maxTurns: 1`:给它们多轮只会让它们反复斟酌,而它们没有新信息可拿。
- `@council` 与角色点名共用 `@` 前缀,展开顺序在 repl.ts 里是硬约定(council 先)。
- 三家的顺序 = 配置文件里的家序(glm → deepseek → claude),不按完成顺序,报告读起来稳定。
